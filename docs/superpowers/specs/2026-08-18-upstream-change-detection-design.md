# 원문 변경 감지 설계

- 작성일: 2026-08-18
- 대상 저장소: `google-cpp-style-guide-kr`
- 관련 파일: `.github/ISSUE_TEMPLATE/upstream-change.yml`(수동 신고용 템플릿, 이 자동화가 그 자리를 대신하지 않고 보완한다)

## 배경

이 저장소는 [Google C++ Style Guide](https://google.github.io/styleguide/cppguide.html)의 한글 번역본이다. 원문이 바뀌면 번역도 따라가야 하지만, 지금은 그 사실을 알아채는 수단이 사람의 기억뿐이다. 원문 변경을 놓치면 번역본은 조용히 낡는다. 독자는 그것이 낡았다는 사실조차 알 수 없다.

원문 저장소(`google/styleguide`)의 `cppguide.html` 커밋 이력을 조사한 결과는 다음과 같다.

| 릴리스 | 변경 섹션 | 추가/삭제 |
| --- | --- | --- |
| 2025-07-31 (`c6f57a91`) | — | 기준점 |
| 2025-11-13 (`c885dc26`) | 11개 | — |
| 2026-05-01 (`3c5c895c`) | 11개 | `Boost` 삭제 → `Third_party_Libraries` 추가 |
| 2026-06-03 (`1809c769`) | 1개 | — |

여기서 두 가지가 드러난다.

1. 변경 빈도는 낮지만(연 2~5회) **한 릴리스가 10개 이상의 섹션을 한꺼번에 건드린다.** "파일이 바뀌었다"는 신호만으로는 어디를 손봐야 할지 알 수 없다.
2. **섹션 추가·삭제가 실제로 일어난다.** 이 경우 번역 본문뿐 아니라 새 `.md` 파일, `scripts/upstream-topic-map.json`, `mkdocs.yml` nav까지 함께 갱신해야 한다.

목표는 원문이 바뀌었을 때 **어느 섹션이 어떻게 바뀌었고, 그것이 어느 번역 파일에 해당하는지**를 자동으로 이슈에 남기는 것이다.

## 전제

원문의 `<h2 id="...">` / `<h3 id="...">` 앵커 113개와 `scripts/upstream-topic-map.json`의 113개 항목이 id 기준으로 정확히 일치한다(2026-08-18 확인). 따라서 감지된 섹션 id를 번역 파일 경로로 곧바로 옮길 수 있다.

이 일치가 깨지는 경우는 원문에 섹션이 추가·삭제될 때뿐이고, 그때는 감지 시스템이 이슈에 "topic-map과 nav도 함께 갱신해야 한다"고 명시한다. 그 외의 불일치(사람이 topic-map을 잘못 건드린 경우)는 기존 `scripts/check_translation_coverage.py`의 영역이므로 여기서 중복 검사하지 않는다.

## 구조

```
주 1회 cron ─→ cppguide.html 내려받기
                    │
                    ├─ 섹션 113개로 분할 (<h2|h3 id="…"> 기준)
                    ├─ 저장된 스냅샷과 섹션별 정규화 텍스트 비교
                    │
              변경 없음 → 종료 (아무 흔적도 남기지 않음)
              변경 있음 → ① 스냅샷 갱신 커밋  ② 이슈 1개 생성
```

## 구성 요소

### `scripts/upstream_sections.py`

파싱과 비교 로직 전부를 담는다. 워크플로는 이 스크립트를 호출만 한다. 로컬에서도 동일하게 실행할 수 있어야 한다. 기존 `scripts/check_translation_coverage.py`와 같은 위치·같은 실행 방식(표준 라이브러리만 사용, 인자 없는 CLI)을 따른다.

하위 명령은 둘뿐이다.

- `snapshot` — 현재 원문을 받아 스냅샷을 다시 쓴다.
- `diff` — 현재 원문과 저장된 스냅샷을 비교해 **이슈 본문용 마크다운을 stdout으로 출력한다.** 변경이 없으면 아무것도 출력하지 않는다.

두 명령 모두 기본적으로 원문을 네트워크에서 받는다. `--source <경로 또는 URL>`로 입력을 바꿀 수 있고, 과거 릴리스 회귀 테스트는 이 옵션으로 수행한다.

**섹션 분할**: `<h2 id>` 또는 `<h3 id>`가 나타나는 지점부터 다음 `<h2|h3 id>` 직전까지를 한 섹션으로 본다.

**정규화**: `<pre>` **바깥**은 태그를 제거하고 공백을 단일 스페이스로 접는다. 산문의 줄바꿈·들여쓰기 변경으로 오탐이 나면 안 되기 때문이다. 이때 `i`, `b`, `em`, `strong`, `code`, `a`, `span`, `tt`, `sub`, `sup` 같은 인라인 태그는 (앞뒤에 공백을 넣지 않고) 통째로 제거한다 — 순수하게 타이포그래피적인 마크업 변화는 내용 변경이 아니라고 보는 의도적 설계다. `<code>` 태그 하나를 추가·삭제하는 원문 편집이 매주 오탐을 만들지 않도록 하는 장치이므로, `normalize`를 고칠 때는 이 규칙을 깨뜨리지 않았는지 확인해야 한다. `<pre>` **안쪽은 공백을 그대로 보존한다.** 코드 예제의 들여쓰기는 스타일 가이드의 내용 그 자체이므로 놓치면 안 된다. HTML 엔티티는 언이스케이프한다.

**비교**: 정규화된 섹션 텍스트를 그대로 문자열 비교한다. 섹션별 SHA-256도 함께 기록하지만, 이는 스냅샷 로드 시 저장된 파일이 매니페스트의 해시와 일치하는지 검증하는 데만 쓰인다 — 나쁜 병합이나 실수로 스냅샷 `.txt`가 손상되면 "원문이 바뀐 것"과 구별할 수 없게 되므로, 그 경우 조용히 덮어쓰는 대신 즉시 실패하기 위해서다. 변경 감지 자체는 해시가 아니라 텍스트 비교로 이루어진다.

### `upstream/` — 스냅샷 저장소

- `upstream/manifest.json` — 원문 커밋 sha, 수집 시각, 섹션별 `{id, level, title, sha256}`
- `upstream/sections/<id>.txt` — 섹션별 정규화 텍스트 113개

mkdocs의 docs 루트가 `google cpp style guide/`이므로 이 디렉터리는 사이트 빌드에 포함되지 않는다.

텍스트 스냅샷을 두는 이유는 `git diff`로 "이 문장이 이렇게 바뀌었다"를 그대로 뽑아 이슈에 붙이기 위해서다. 해시만 두면 "바뀌었다"까지만 말할 수 있다.

### `.github/workflows/upstream-watch.yml`

- 트리거: `schedule`(매주 월요일 00:00 UTC) + `workflow_dispatch`
- 권한: `contents: write`, `issues: write`
- 흐름: `diff` 실행 → 출력이 비어 있으면 종료 → 비어 있지 않으면 `diff` 출력을 본문으로 이슈부터 생성하고, 그다음 `snapshot` 실행 후 커밋·푸시(이슈 생성 실패보다 스냅샷 푸시 실패가 복구하기 쉬우므로 이 순서를 지킨다)

기존 `gh-pages.yml`과 같은 형식(`actions/checkout@v4`, `actions/setup-python@v5`, Python 3.11)을 따른다.

## 이슈 형식

제목: `원문 변경 감지: 2026-06-09 (1809c769)`

날짜는 원문 릴리스 날짜가 아니라 **감지 시각**(워크플로 실행 시각)이다. 주 1회
cron이므로 실제 원문 커밋 날짜(`1809c769`는 2026-06-03)보다 최대 6일 늦을 수
있다.

본문 구성:

1. 변경 섹션 표 — 섹션 id · 원문 제목 · 번역 파일 · 변경 종류(수정/추가/삭제)
2. 번역 파일별 체크박스
3. 섹션별 diff 발췌 — `<details>`로 접어 둔다
4. 원문 GitHub compare 링크 (`이전 sha…현재 sha`)

라벨은 기존 `.github/ISSUE_TEMPLATE/upstream-change.yml`과 동일하게 `documentation`, `enhancement`.

**추가·삭제된 섹션은 별도 블록으로 분리한다.** 이때는 번역 본문 외에 새 `.md` 파일 생성, `upstream-topic-map.json`, `mkdocs.yml` nav 갱신이 함께 필요하다는 점을 이슈에 명시한다.

## 설계 결정

**스냅샷은 감지 즉시 갱신한다.** diff는 이슈 본문에 이미 박제되므로 스냅샷을 붙들고 있을 이유가 없고, 미루면 다음 주 실행에서 같은 변경으로 이슈가 중복 생성된다. 스냅샷 갱신은 "감지했음" 표시이지 "번역 반영 완료" 표시가 아니다. 완료 추적은 이슈가 한다.

**릴리스당 이슈 하나.** 한 릴리스가 11개 섹션을 건드리는 분포에서 섹션당 이슈를 만들면 알림이 한꺼번에 11개 열린다. 표와 체크박스로 한 이슈에 모으고, 필요하면 사람이 거기서 세부 이슈를 딴다.

**원문 커밋 sha를 기록한다.** 봇이 만든 발췌를 믿기 어려울 때 원문 diff로 바로 넘어갈 수 있어야 한다.

**topic-map 동기화도 함께 검사한다.** 추가·삭제된 섹션은 곧 `upstream-topic-map.json`과 `mkdocs.yml`의 갱신 대상이므로, 불일치를 이슈에 함께 적는다.

## 오류 처리

- **원문 내려받기 실패**: 워크플로를 실패시킨다. 조용히 넘어가면 감지가 멈춘 것을 알 수 없다.
- **섹션 파싱 결과가 비정상**(섹션 수가 90개 미만): 스냅샷을 갱신하지 않고 워크플로를 실패시킨다. 현재 113개이고 한 릴리스에서 20개 이상이 한꺼번에 사라진 적은 없으므로, 그런 결과는 원문 구조 변경이나 응답 오류로 본다. 원문 사이트가 구조를 바꾸거나 오류 페이지를 반환한 경우 스냅샷을 망가뜨리면 안 된다.
- **이슈 생성 실패**: 워크플로를 실패시킨다. 이슈가 스냅샷 갱신보다 먼저 실행되므로 이 시점에는 아직 스냅샷이 푸시되지 않았고, 실패 로그의 diff 출력으로 수동 복구한다.
- **스냅샷 커밋·푸시 실패**: 워크플로를 실패시킨다. 이슈는 이미 생성된 뒤이므로 사람이 할 일은 없다. 다음 실행이 같은 변경을 다시 감지해 스냅샷을 갱신하며, 그 결과 중복 이슈가 하나 열릴 수 있지만 이는 눈에 보이고 쉽게 닫을 수 있는 비용이다.

## 검증

1. **과거 릴리스 회귀 테스트**: `c6f57a91` → `c885dc26` → `3c5c895c` → `1809c769` 순으로 흘려 넣어 변경 섹션 수가 **11 / 11+추가1+삭제1 / 1** 로 재현되는지 확인한다. 이 기준값은 2026-08-18에 측정했다.
2. **정규화 검증**: 산문의 줄바꿈만 바꾼 입력에서는 변경이 감지되지 않고, `<pre>` 안의 들여쓰기만 바꾼 입력에서는 감지되는지 확인한다.
3. **워크플로 수동 실행**: `workflow_dispatch`로 1회 실행해 이슈가 실제로 열리는지 확인하고, 곧바로 재실행해 조용히 끝나는지 확인한다.
