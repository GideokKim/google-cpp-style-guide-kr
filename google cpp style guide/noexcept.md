# noexcept (noexcept)

## 원문 규칙 번역

유용하고 올바른 경우에는 noex를 지정하십시오.

noException 지정자는 함수가 예외를 발생시킬지 여부를 지정하는 데 사용됩니다. noException 으로 표시된 함수에서 예외가 발생하면 프로그램은 std::terminate 를 통해 충돌합니다.

noException 연산자는 표현식이 예외를 발생시키지 않도록 선언된 경우 true를 반환하는 컴파일 타임 검사를 수행합니다.

- 이동 생성자를 noException으로 지정하면 경우에 따라 성능이 향상됩니다. 예를 들어 T의 이동 생성자가 noException인 경우 std::Vector<T>::resize()는 객체를 복사하는 대신 이동합니다.
- 함수에 noException을 지정하면 예외가 활성화된 환경에서 컴파일러 최적화가 트리거될 수 있습니다. 예를 들어 컴파일러는 noException 지정자로 인해 예외가 발생할 수 없다는 것을 알고 있는 경우 스택 해제를 위한 추가 코드를 생성할 필요가 없습니다.

- 예외가 비활성화된 이 가이드를 따르는 프로젝트에서는 noException 지정자가 올바른지 확인하기 어렵고 정확성이 무엇을 의미하는지 정의하기도 어렵습니다.
- 불가능하지는 않더라도 호출자가 의존할 수 있는 보장을 감지하기 어려운 방식으로 제거하기 때문에 noexp를 실행 취소하는 것은 어렵습니다.

함수의 의도된 의미를 정확하게 반영하는 경우, 즉, 함수 본문 내에서 예외가 발생하면 치명적인 오류를 나타내는 경우 성능에 유용할 때 noException을 사용할 수 있습니다. 이동 생성자에 대한 noException이 의미 있는 성능 이점을 제공한다고 가정할 수 있습니다. 다른 기능에 noException을 지정하면 상당한 성능 이점이 있다고 생각되면 프로젝트 리더와 논의하세요.

예외가 완전히 비활성화된 경우(즉, 대부분의 Google C++ 환경)에는 무조건 no제외를 선호합니다. 그렇지 않으면, 함수가 잠재적으로 발생할 수 있는 소수의 경우에만 false를 평가하는 방식으로 간단한 조건과 함께 조건부 noException 지정자를 사용하십시오. 테스트에는 관련 작업이 발생할 수 있는지 여부(예: 이동 생성 객체의 경우 std::is_nothrow_move_constructible) 또는 할당이 발생할 수 있는지 여부(예: 표준 기본 할당의 경우 absl::default_allocator_is_nothrow)에 대한 유형 특성 검사가 포함될 수 있습니다. 대부분의 경우 예외의 유일한 원인은 할당 실패(할당 실패로 인한 경우를 제외하고는 이동 생성자가 발생해서는 안 된다고 생각함)이며, 메모리 고갈을 프로그램에서 복구를 시도해야 하는 예외 조건이 아닌 치명적인 오류로 처리하는 것이 적절한 응용 프로그램이 많이 있습니다. 다른 잠재적인 실패의 경우에도 가능한 모든 예외 발생 시나리오를 지원하는 것보다 인터페이스 단순성에 우선순위를 두어야 합니다. 해시 함수가 발생시킬 수 있는지 여부에 따라 복잡한 noException 절을 작성하는 대신 예를 들어 구성 요소가 해시 함수 발생을 지원하지 않는다는 점을 문서화하고 무조건 noException으로 만드세요.

## 이해하기 쉽게 설명하기

noexcept 규칙을 적용할 때는 원문 규칙을 문자 그대로 외우기보다, 왜 이 선택이 독자에게 더 명확한지 살펴보면 쉽습니다. 코드 리뷰에서는 이 기능이 호출 지점에서 의도를 숨기지 않는지, 더 단순한 구조로 같은 목적을 달성할 수 없는지, 기존 코드와 섞였을 때 유지보수 비용이 커지지 않는지를 확인하세요.
