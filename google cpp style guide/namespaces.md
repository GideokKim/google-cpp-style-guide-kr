# Namespaces (Namespaces)

## 원문 규칙 번역

몇 가지 예외를 제외하고 코드를 네임스페이스에 배치합니다. 네임스페이스는 프로젝트 이름과 경로에 따라 고유한 이름을 가져야 합니다. using 지시문을 사용하지 마세요(예: 네임스페이스 foo 사용). 인라인 네임스페이스를 사용하지 마세요. 이름이 지정되지 않은 네임스페이스에 대해서는 내부 연결을 참조하세요.

네임스페이스는 전역 범위를 별개의 명명된 범위로 세분화하므로 전역 범위에서 이름 충돌을 방지하는 데 유용합니다.

네임스페이스는 대부분의 코드가 합리적으로 짧은 이름을 사용할 수 있도록 허용하면서 대규모 프로그램에서 이름 충돌을 방지하는 방법을 제공합니다.

예를 들어 두 개의 다른 프로젝트에 전역 범위에 Foo 클래스가 있는 경우 이러한 기호는 컴파일 타임이나 런타임에 충돌할 수 있습니다. 각 프로젝트가 자신의 코드를 네임스페이스에 배치하는 경우 project1::Foo 및 project2::Foo는 이제 충돌하지 않는 고유한 기호이며 각 프로젝트 네임스페이스 내의 코드는 접두사 없이 계속 Foo를 참조할 수 있습니다.

인라인 네임스페이스는 해당 이름을 바깥쪽 범위에 자동으로 배치합니다. 예를 들어 다음 스니펫을 고려해보세요.

```cpp
namespace outer {
inline namespace inner {
  void foo();
}  // namespace inner
}  // namespace outer
```

외부::inner::foo() 및 외부::foo() 표현식은 서로 바꿔 사용할 수 있습니다. 인라인 네임스페이스는 주로 버전 간 ABI 호환성을 위해 만들어졌습니다.

네임스페이스는 이름이 참조하는 정의를 파악하는 메커니즘을 복잡하게 만들기 때문에 혼란스러울 수 있습니다.

특히 인라인 네임스페이스는 이름이 실제로 선언된 네임스페이스로 제한되지 않기 때문에 혼란스러울 수 있습니다. 이는 일부 대규모 버전 관리 정책의 일부로만 유용합니다.

일부 상황에서는 정규화된 이름으로 기호를 반복적으로 참조해야 합니다. 깊게 중첩된 네임스페이스의 경우 이로 인해 많은 혼란이 추가될 수 있습니다.

네임스페이스는 다음과 같이 사용해야 합니다.

- 네임스페이스 이름에 대한 규칙을 따르십시오.
- 주어진 예에 표시된 대로 주석으로 여러 줄의 네임스페이스를 종료합니다.
- 네임스페이스는 다른 네임스페이스의 클래스에 대한 포함, gflags 정의/선언 및 전방 선언 뒤에 전체 소스 파일을 래핑합니다. // .h 파일 네임스페이스 mynamespace { // 모든 선언은 네임스페이스 범위 내에 있습니다. // 들여쓰기가 부족하다는 점에 주목하세요. class MyClass { 공개: ... void Foo(); }; } // 네임스페이스 mynamespace // .cc 파일 네임스페이스 mynamespace { // 함수 정의는 네임스페이스 범위 내에 있습니다. void MyClass::Foo() { ... } } // 네임스페이스 mynamespace 더 복잡한 .cc 파일에는 플래그 또는 using 선언과 같은 추가 세부 정보가 있을 수 있습니다. #include "a.h" ABSL_FLAG(bool, someflag, false, "a 플래그"); 네임스페이스 mynamespace { 사용::foo::Bar; ...code for mynamespace... // 코드는 왼쪽 여백에 맞춰집니다. } // 네임스페이스 mynamespace
- 생성된 프로토콜 메시지 코드를 네임스페이스에 배치하려면 .proto 파일에서 패키지 지정자를 사용하세요. 자세한 내용은 프로토콜 버퍼 패키지를 참조하세요.
- 표준 라이브러리 클래스의 전방 선언을 포함하여 std 네임스페이스에 어떤 것도 선언하지 마세요. std 네임스페이스에서 엔터티를 선언하는 것은 정의되지 않은 동작입니다. 즉, 이식성이 없습니다. 표준 라이브러리에서 엔터티를 선언하려면 적절한 헤더 파일을 포함하십시오.
- 네임스페이스의 모든 이름을 사용 가능하게 만들기 위해 using 지시문을 사용할 수 없습니다. // 금지됨 - 이는 네임스페이스를 오염시킵니다. 네임스페이스 foo 사용;
- 명시적으로 표시된 내부 전용 네임스페이스를 제외하고 헤더 파일의 네임스페이스 범위에서 네임스페이스 별칭을 사용하지 마세요. 헤더 파일의 네임스페이스로 가져온 모든 항목은 해당 파일에서 내보낸 공용 API의 일부가 되기 때문입니다. 해당 조건이 적용되지 않는 경우 네임스페이스 별칭을 사용할 수 있지만 적절한 이름이 있어야 합니다. // .h 파일에서 별칭은 별도의 API가 아니거나 // 구현 세부정보에 숨겨야 합니다. 네임스페이스 라이브러리언 { 네임스페이스 내부 { // 내부, API의 일부가 아닙니다. 네임스페이스 사이드테이블 = ::pipeline_diagnostics::sidetable; } inline void my_inline_function() { // 함수에 로컬입니다. 네임스페이스 baz = ::foo::bar::baz; ... } } // 네임스페이스 라이브러리언 // .cc 파일에서 일반적으로 사용되는 이름 중 흥미롭지 않은 부분을 제거합니다. 네임스페이스 사이드테이블 = ::pipeline_diagnostics::sidetable;
- 인라인 네임스페이스를 사용하지 마세요.
- API 사용자가 언급해서는 안 되는 API 부분을 문서화하려면 이름에 "internal"이 포함된 네임스페이스를 사용하세요. // ABSL이 아닌 코드에서는 이 내부 이름을 사용하면 안 됩니다. ::absl::container_internal::ImplementationDetail 사용; 중첩된 내부 네임스페이스 내의 라이브러리 간에는 여전히 충돌 위험이 있으므로 라이브러리의 파일 이름을 추가하여 네임스페이스 내의 각 라이브러리에 고유한 내부 네임스페이스를 제공합니다. 예를 들어 gshoe/widget.h는 gshoe::internal이 아닌 gshoe::internal_widget을 사용합니다.
- 새 코드에서는 한 줄로 중첩된 네임스페이스 선언이 선호되지만 필수는 아닙니다. 네임스페이스 my_project::my_comComponent { ... } // 네임스페이스 my_project::my_comComponent

## 이해하기 쉽게 설명하기

이 규칙의 핵심은 해당 조건이 적용되지 않는 경우 네임스페이스 별칭을 사용할 수 있지만 적절한 이름이 있어야 합니다.

실제로 코드를 볼 때는 ::absl::container_internal::ImplementationDetail 사용; 중첩된 내부 네임스페이스 내의 라이브러리 간에는 여전히 충돌 위험이 있으므로 라이브러리의 파일 이름을 추가하여 네임스페이스 내의 각 라이브러리에 고유한 내부 네임스페이스를 제공합니다.

점검할 때는 특히 다음을 확인하세요:

- 각 프로젝트가 자신의 코드를 네임스페이스에 배치하는 경우 project1::Foo 및 project2::Foo는 이제 충돌하지 않는 고유한 기호이며 각 프로젝트 네임스페이스 내의 코드는 접두사 없이 계속 Foo를 참조할 수 있습니다.
- 네임스페이스는 대부분의 코드가 합리적으로 짧은 이름을 사용할 수 있도록 허용하면서 대규모 프로그램에서 이름 충돌을 방지하는 방법을 제공합니다.
