# 템플릿 메타프로그래밍 (Template Metaprogramming)

## 원문 규칙 번역

복잡한 템플릿 프로그래밍을 피하세요.

템플릿 메타프로그래밍은 C++ 템플릿 인스턴스화 메커니즘이 Turing 완전하고 유형 도메인에서 임의의 컴파일 시간 계산을 수행하는 데 사용될 수 있다는 사실을 활용하는 기술 계열을 나타냅니다.

템플릿 메타프로그래밍을 사용하면 유형이 안전하고 고성능인 매우 유연한 인터페이스가 가능합니다. GoogleTest , std::tuple , std::function 및 Boost.Spirit 과 같은 기능은 이것이 없으면 불가능합니다.

템플릿 메타프로그래밍에 사용되는 기술은 언어 전문가 외에는 누구에게도 모호한 경우가 많습니다. 템플릿을 복잡한 방식으로 사용하는 코드는 읽을 수 없고 디버깅이나 유지 관리가 어려운 경우가 많습니다.

템플릿 메타프로그래밍은 종종 극도로 열악한 컴파일 시간 오류 메시지로 이어집니다. 인터페이스가 단순하더라도 사용자가 뭔가 잘못하면 복잡한 구현 세부 사항이 표시됩니다.

템플릿 메타프로그래밍은 리팩토링 도구 작업을 더 어렵게 만들어 대규모 리팩토링을 방해합니다. 첫째, 템플릿 코드가 여러 컨텍스트에서 확장되므로 변환이 모든 컨텍스트에서 의미가 있는지 확인하기가 어렵습니다. 둘째, 일부 리팩토링 도구는 템플릿 확장 후 코드 구조만 나타내는 AST와 함께 작동합니다. 다시 작성해야 하는 원래 소스 구성으로 자동으로 작업하는 것은 어려울 수 있습니다.

템플릿 메타프로그래밍은 때로 그것 없이는 가능한 것보다 더 깨끗하고 사용하기 쉬운 인터페이스를 허용하지만 종종 지나치게 영리한 유혹을 받기도 합니다. 추가 유지 관리 부담이 많은 용도로 분산되는 소수의 낮은 수준 구성 요소에 사용하는 것이 가장 좋습니다.

템플릿 메타프로그래밍이나 기타 복잡한 템플릿 기술을 사용하기 전에 두 번 생각하십시오. 일반 팀원이 다른 프로젝트로 전환한 후에도 코드를 유지할 수 있을 만큼 코드를 잘 이해할 수 있는지, C++ 프로그래머가 아니거나 코드베이스를 우연히 검색하는 사람이 오류 메시지를 이해하거나 호출하려는 함수의 흐름을 추적할 수 있는지 생각해 보세요. 재귀 템플릿 인스턴스화, 유형 목록, 메타 함수 또는 표현식 템플릿을 사용하거나 함수 오버로드 해결을 감지하기 위해 SFINAE 또는 sizeof 트릭을 사용하는 경우 너무 멀리 갔을 가능성이 높습니다.

템플릿 메타프로그래밍을 사용하는 경우 복잡성을 최소화하고 격리하는 데 상당한 노력을 기울여야 합니다. 가능하면 메타프로그래밍을 구현 세부 사항으로 숨겨 사용자가 보는 헤더를 읽을 수 있도록 해야 하며 까다로운 코드에는 특히 주석이 잘 달렸는지 확인해야 합니다. 코드가 어떻게 사용되는지 주의 깊게 문서화해야 하며 "생성된" 코드가 어떻게 생겼는지에 대해 설명해야 합니다. 사용자가 실수할 때 컴파일러가 내보내는 오류 메시지에 각별히 주의하세요. 오류 메시지는 사용자 인터페이스의 일부이므로 사용자 관점에서 오류 메시지를 이해하고 조치를 취할 수 있도록 필요에 따라 코드를 조정해야 합니다.

## 이해하기 쉽게 설명하기

이 규칙의 핵심은 재귀 템플릿 인스턴스화, 유형 목록, 메타 함수 또는 표현식 템플릿을 사용하거나 함수 오버로드 해결을 감지하기 위해 SFINAE 또는 sizeof 트릭을 사용하는 경우 너무 멀리 갔을 가능성이 높습니다.

실제로 코드를 볼 때는 가능하면 메타프로그래밍을 구현 세부 사항으로 숨겨 사용자가 보는 헤더를 읽을 수 있도록 해야 하며 까다로운 코드에는 특히 주석이 잘 달렸는지 확인해야 합니다.

점검할 때는 특히 다음을 확인하세요:

- 오류 메시지는 사용자 인터페이스의 일부이므로 사용자 관점에서 오류 메시지를 이해하고 조치를 취할 수 있도록 필요에 따라 코드를 조정해야 합니다.
- 코드가 어떻게 사용되는지 주의 깊게 문서화해야 하며 "생성된" 코드가 어떻게 생겼는지에 대해 설명해야 합니다.
